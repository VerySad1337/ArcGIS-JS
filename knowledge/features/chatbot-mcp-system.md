# Chatbot / MCP System

**Purpose:** An in-app chatbot, backed by a locally-hosted (Ollama) language model, that can search the configured ArcGIS Portal, query/aggregate feature layers already on the user's map, and drive `AnalysisPanel.jsx`/`LayerControlPanel.jsx`'s own tooling (heatmap/hexagon analysis, buffer, portal layer add, filter, style, toggle, zoom) - all via [MCP](https://modelcontextprotocol.io) tool definitions, and with the model itself running entirely within the operator's own infrastructure so no map/portal context is sent to a third-party API.

**Key Files:**
- `mcp-chat-proxy/` (repo root) - the new sidecar. `server.js` (routes), `chatLoop.js` (orchestration), `mcpServer.js` (the real MCP server), `portalTools.js` (shared tool implementations), `toolSchemas.js` (every tool's schema, tagged `server`/`client`), `urlSafety.js` (SSRF guard), `ollamaClient.js`, `config.js`.
- `src/services/ChatService.js` - `sendChatMessage`/`sendToolResult`, same-origin calls to `mcp-chat-proxy` via nginx.
- `src/components/ChatPanel.jsx` - the "CHAT" sidebar card.
- `src/app/ApplicationShell.jsx` - `mapContext`, `handleSendChatMessage`/`handleSubmitChatToolResult`, `runClientAction`.
- `src/gis/GISMapEngine.js` - `getLayers()` now includes a `url` field on every URL-backed layer entry (touristAttractions/mrtStations/mrtLines/portal layers/named heatmap layers), purely for `mapContext.queryableLayerUrls` - no other UI reads it. `inferFieldForValue(id, value)` is this feature's one added engine method (read-only; no UI path calls it).

## The one constraint that shapes the whole design

Per `knowledge/architecture.md`, all map/layer state lives in exactly one place: the browser-resident `GISMapEngine` instance, held via `useRef` in `ApplicationShell`. A server process - including this new sidecar - has no access to it and never gets a shadow copy. That rules out "the MCP server just executes every tool," and splits the tool set into two domains:

- **Server-executed tools** (`toolSchemas.js`'s `SERVER_TOOLS`, real MCP tools registered in `mcpServer.js`): `search_portal_layers`, `query_layer_features`, `get_layer_statistics` - all backed by ArcGIS REST calls the sidecar can make directly, no browser dependency. `chatLoop.js` executes these in-process (calling `portalTools.js` directly, the same functions `mcpServer.js` wraps for any external MCP client hitting `POST /mcp`) and loops, feeding the result back to Ollama, until it gets plain text or a client-tool call.
- **Client-executed tools** (`CLIENT_TOOLS`): `create_heatmap_layer`, `create_hexagon_layer`, `apply_buffer`, `create_buffer_result_layer`, `add_portal_layer`, `set_layer_filter`, `set_layer_style`, `toggle_layer`, `zoom_to_layer`. None of these mutate the map server-side - their schemas exist so Ollama can call them, and `chatLoop.runLoop` stops and returns `{ reply: null, pendingAction: { name, args, callId } }` instead of touching `GISMapEngine`. `add_portal_layer` is the one exception with real server-side logic before that handoff: see below.

## The pendingAction / tool-result protocol

`mcp-chat-proxy` is stateless (same as `onemap-proxy` - no session, no DB): the full `messages` array is round-tripped by the frontend on every call.

1. `ChatPanel.handleSubmit` → `ChatService.sendChatMessage(messages, mapContext)` → `POST /api/chat/message`.
2. If the reply is plain text, `chatLoop` returns it and the turn ends.
3. If Ollama called a client tool, the response carries `pendingAction: { name, args, callId }` instead. `ChatPanel.handleLoopResult` calls `ApplicationShell`'s `runClientAction(name, args)`, which dispatches to the real `GISMapEngine`/`ApplicationShell` method (the same one the manual UI button for that action calls - `engine.createHeatmapLayer`, `engine.addPortalLayer`, etc.), shows the same toast that action would show from the UI, and returns `{ ok, data }` or `{ ok: false, error }`.
4. `ChatPanel` calls `ChatService.sendToolResult(result.messages, mapContext, callId, outcome)` → `POST /api/chat/tool-result`, which appends a `role: "tool"` message with that outcome and resumes the same loop - so the model's next reply reflects what actually happened, not just what it asked for.
5. A single user turn can chain multiple client actions this way (e.g. "add the parks layer and buffer it"); `ChatPanel`'s `MAX_ACTION_CHAIN` (5) is a client-side runaway guard, separate from `mcp-chat-proxy/config.js`'s `maxServerToolHops` (6) which caps server-tool round trips within one HTTP call - the two guards exist because the server's hop counter resets on every `/api/chat/tool-result` call and doesn't by itself bound a long client-action chain across many such calls.

`runClientAction` is deliberately its own function, not a reuse of the existing `createHeatmapLayer`/`createHexagonLayer`/... `useCallback`s in `ApplicationShell` - those already catch-and-toast internally with no return value, but the chat loop needs a real success/failure outcome to report back to the model. It calls `engineRef.current` directly instead, inside its own try/catch, and still shows the identical toast those handlers would have shown - so a chat-driven action looks, to the user watching the map, exactly like the equivalent manual click, and inherits the exact same anonymous-first authorization checks (`IdentityManager`/`canEdit`) those engine methods already enforce. Every *action* reuses an existing engine method; the one engine method this feature added, `inferFieldForValue`, performs no mutation at all (see "Giving the model facts..." below).

## Giving the model facts instead of asking it to guess

Every reliability problem this feature has hit in production has the same shape: a small local model was asked to supply a value only the browser knew, and it invented one. The fixes are correspondingly uniform - supply the fact up front, correct what can be corrected deterministically, and make the remaining failure informative rather than bare. Three instances so far: the portal item id/url (`resolveAddPortalLayerItem`), the custom display name (`renameOwedAfterAdd`, both under Security below), and field names:

**Field names are in the map context, corrected on arrival, and enumerated on failure (2026-08).** Observed directly: "Filter out tampines mrt stations from mrt stations and zoom to layer" had `qwen2.5:1.5b` call `set_layer_filter` with `field: "name"`, which `GISMapEngine.setLayerFilter` → `LayerFilterExpression.resolveField` rejected with `"name" is not a field on this layer.` (exact-match validation against the layer's schema). The model had no way to know the real, conventionally-uppercase field name - nothing in the request told it - so it lowercased a plausible one. `zoom_to_layer` then never ran, because the chain stopped at the failure. Three changes, at three different layers:

1. **`mapContext.layers` now carries each layer's real `fields`** (`ApplicationShell`'s `chatLayerFields` state, prefetched via the existing `GISMapEngine.getLayerFieldSchema` for every `getFilterableLayers()` entry), so the model can name a real field on its *first* attempt. This is not a cosmetic saving: on CPU-only Ollama one turn is dominated by prompt evaluation (~200s - see `mcp-chat-proxy/config.js`'s timeout note), so an avoidable failed round trip costs the user minutes while the extra few hundred prompt tokens cost nothing. The effect is keyed off the layer-id list, deliberately **not** off `layers` itself: `refreshLayers()` fires on every layer mutation including a colour-picker drag, and re-querying every schema on each of those events would spawn a promise per layer per drag event. Trade-off: a field added by `addColumnToLayer` after that ran isn't reflected until the layer set next changes - covered by (2)/(3), which read the live schema. Gated on `CHAT_ENABLED`, so a chat-disabled deployment does no schema prefetching at all.
2. **`runClientAction`'s `set_layer_filter` resolves each condition's `field` against the live schema before the engine sees it** - exact, then case-insensitive, then ignoring separators (so `name`/`station_name`/`Station Name` reach `NAME`/`STATION_NAME`). Nothing looser is attempted on purpose: silently filtering on a field the user didn't ask about is worse than an error. The strictness stays where it belongs - the manual Filter UI populates its field `<select>` from `getLayerFieldSchema` and so can never send a bad field, which is why `GISMapEngine`/`LayerFilterExpression` are unchanged and still exact-match; the leniency is specific to a field name a *model* typed.
3. **An unresolvable field fails with the layer's actual field list** (`'"nope" is not a field on "MRT Stations", and no field on it contains "Tampines". Its fields are: OBJECTID_1, TYPE, NAME, ... Retry with one of those exact names.'`) instead of the engine's bare message, so the model's retry is informed rather than another guess. Un-toasted, like `add_portal_layer`'s invalid-item branch: it's a recoverable, model-facing correction mid-turn, not a user-facing failure.

**The informative error was not enough - the model doesn't retry, so the field is now inferred from the data (2026-08).** Re-running the same request after (1)-(3) produced the *same class* of failure with a different invented name: `field: "title"`, which failed with the field list `OBJECTID_1, TYPE, NAME, Shape__Area, Shape__Length` - and the model then simply relayed that list to the user as advice ("Please try filtering on one of the other fields like...") instead of retrying with `NAME`. Handing a small model better information does not make it act on it. So the last guess is removed too:

- **`GISMapEngine.inferFieldForValue(id, value)`** (a genuinely new engine method - the first this feature required, since it needs live layer access no existing method exposed) asks the *service* which field holds the value, rather than reasoning about field names at all: it runs the same `UPPER(f) LIKE UPPER('%value%')`-across-every-string-field query `searchHostedLayer` already uses for global feature search, then reads the one matched feature's attributes back to see which candidate field the value actually appeared in. One round trip, returning `{ field, matchedValue }`. A value like "Tampines" identifies its own field far more reliably than a 1.5B model does. Returns null for `drawings`/any `GraphicsLayer` (no `queryFeatures`), a layer with no string fields, or a value no feature contains - the caller then falls back to (3)'s error. Query failures are caught and returned as null rather than thrown, same as `searchHostedLayer`.
- **`runClientAction` calls it whenever the model's field name doesn't resolve**, and only then - a field that resolves is never second-guessed.
- **`=` is promoted to `contains` on evidence from that same probe.** `NAME = 'Tampines'` provably matches nothing when the real value is `TAMPINES MRT STATION`, which would apply a filter that silently empties the layer - a worse outcome than the error, because it looks like it worked. The promotion fires only when the probe found the value as a strict substring of the matched value; when the value *is* the whole field value, `=` is left alone. This is the one place the app changes the *meaning* of what the model asked for, and it does so on a fact read from the data, never on a hunch.
- **Every substitution is reported back in the tool result as a `corrections` array**, and `buildSystemMessage` instructs the model to describe what actually ran in those terms rather than what it asked for. Silently correcting a field would otherwise just move the false-reporting problem: the model would confidently tell the user it filtered on `title`.

**Round three: the operator, the intent, the dropped second action, and two bugs outside the chat entirely (2026-08).** With the field resolved from the data, `docker logs` (added for exactly this purpose) finally showed what the model was really sending for "Filter out tampines mrt stations from mrt stations and zoom to layer":

```
tool call: set_layer_filter {"id":"mrtStations","conditions":[{"field":"title","operator":"=","value":"Tampines"}]}
tool call: set_layer_filter {"id":"mrtStations","conditions":[{"field":"title","operator":"<>","value":"Tampines"}]}
```

Four separate defects, only two of which were chat-specific:

1. **`<>` on a substring value is a filter that applies cleanly and filters nothing.** `NAME <> 'Tampines'` is true of every station, since none is *exactly* "Tampines". The `=` → `contains` promotion above was therefore only half a fix; `<>` → `doesNotContain` is its mirror, on the same probe evidence, preserving include-vs-exclude intent. `doesNotContain` did not exist and had to be added to `LayerFilterExpression.js` - see `knowledge/index.md`'s Filter & Aggregate System for that operator, which the manual Filter UI now offers too.
2. **The model read "filter out X" as exclusion; this app's users mean narrowing.** Unlike a field name, intent is not in the data - there is nothing to probe - so `chatLoop.js`'s `applyFilterIntent` reads it off the user's own phrasing before the action leaves the server: `NARROWING_PHRASES` ("filter out/for/to", "show only", "just the", "isolate", "narrow to", "find") flip `<>`→`=` and `doesNotContain`→`contains`; `EXCLUDING_PHRASES` ("exclude", "remove", "hide", "omit", "except", "without", "all but", "don't show") flip the other way. Applied **only when the phrasing is one-sided** - if both kinds of wording appear, or neither does, the model's own choice stands rather than being flipped on a coin toss. The corroborating evidence that narrowing is the intended reading: the same request asked to *zoom to the layer afterward to see the specific station*, which only makes sense once the layer has been narrowed down to it.
3. **`zoom_to_layer` was never called at all.** The logs show two filter calls and nothing else - the model spent its turn retrying the filter and silently dropped the second half of the request. `ChatPanel` executes one client action per assistant turn by design, so a two-part request depends entirely on the model asking again once it sees the first outcome, which this model does not reliably do. This is the *same* failure as the dropped rename, so it gets the same treatment: `zoomOwedAfterFilter` derives the zoom from the user's own phrasing (`ZOOM_REQUEST`) after a successful `set_layer_filter` and emits it as a `pendingAction` with no model turn involved. `submitToolResult` now tries each derivation in turn (`derivedFollowUp`), and `alreadyZoomedTo` suppresses it when the model did call `zoom_to_layer` itself, so one request never moves the camera twice.
4. **Two defects that were never about the chat.** Both were exposed by a chat request and both were equally reachable from the manual UI: `zoomToLayer` framed `fullExtent` (the *service's* extent, which ignores `definitionExpression`), so zooming a layer filtered to one station framed every station in the country; and `LayerControlPanel`'s Filter form showed a blank condition row beside its own "filtered" badge, where pressing Apply Filter would have cleared the filter. Both are documented in `knowledge/index.md` (Zoom to layer; Filter & Aggregate System) rather than here, because neither belongs to this feature - a chat that drives the same engine methods the UI drives will keep surfacing UI bugs this way, and they should be fixed where they live.

**Separately: the tool schema advertised three operators the engine has never supported (2026-08).** `set_layer_filter`'s `operator` enum listed `"!="`, `"is null"` and `"is not null"`; `LayerFilterExpression.js`'s `FILTER_OPERATORS` table keys those as `"<>"`, `"isNull"` and `"isNotNull"`, and an unknown token throws `'"!=" is not a supported filter operator.'` This was latent but squarely in the path of the reported request - `!=` is the obvious operator for "filter **out** Tampines", so the field bug was simply hiding it. The enum is now `FILTER_OPERATORS`' real keys verbatim (including the previously unadvertised `startsWith`/`endsWith`), with a description telling the model that `<>` excludes and that `contains` is usually the right choice for a name that may be part of a longer value. `runClientAction` additionally maps the three old spellings (plus `like`/`starts with`/`ends with`) onto the real tokens, because a model will keep emitting SQL-flavoured operators no matter what the enum says.

**The model also fabricated the outcome, which is its own bug.** It told the user the filter "has been successfully applied" and attributed the error to a `zoom_to_layer` call it had never made - the exact same false-success pattern as the rename saga below, and the reason `buildSystemMessage` now carries an explicit rule: an `ok: false` tool result means the action did **not** happen, must be reported as failed, must not be blamed on a different action, and only actions actually called and observed may be described. Worth noting what this does and does not buy: a prompt rule cannot *make* a small model honest, which is precisely why (1)-(3) above remove the failure rather than relying on it being reported well.

Covered by `ApplicationShell.test.jsx`'s `runClientAction set_layer_filter field resolution` describe block and `"the chat map context carries each layer's real field names"`.

## Security

- **SSRF.** `query_layer_features`/`get_layer_statistics` take a `url`. Two independent guards apply: `urlSafety.js`'s `resolveSafeAddress` rejects anything non-`https`, loopback, private, or link-local (applies to every caller, including an external MCP client hitting `/mcp` directly, which has no app context at all); `chatLoop.js`'s `assertUrlIsOnCurrentMap` additionally rejects any URL not present in that request's `mapContext.queryableLayerUrls` (the in-app-chat-specific, tighter restriction - only a layer already on the user's map, not just any public ArcGIS service). `resolveSafeAddress` returns the exact IP it validated, and `portalTools.js`'s `fetchJson` pins the actual outbound connection to that literal address (via undici's per-request `dispatcher`/`connect.lookup`) rather than letting `fetch()` re-resolve the hostname on its own - a naive "validate the hostname, then fetch the hostname" flow is vulnerable to DNS rebinding (a short-TTL record that's public at check time and private/loopback by the time the real request fires), which this closes. Redirects are rejected outright rather than followed, since a redirect target has never itself been validated.
- **No free-text portal adds - resolved server-side, not just prompted.** `add_portal_layer`'s tool description asks the model to use an item from a prior `search_portal_layers` call, but a system-prompt instruction alone isn't enforcement: observed directly in production, `qwen2.5:1.5b` asked to add "Singapore Country Boundary" skipped calling `search_portal_layers` and fabricated a plausible-looking URL instead (pattern-matched off this app's own known org id) - a 400 from ArcGIS that the model then misreported to the user as an access/login problem. `chatLoop.js`'s `resolveAddPortalLayerItem` treats the model's `item.id`/`item.url` as untrusted hints it never acts on directly - only `item.title` is used, as a lookup key: fuzzy-matched (`titleSimilarity`, word-overlap scoring with a normalized-substring fast path) first against every item `search_portal_layers` has actually returned so far this conversation (`knownPortalItems(messages)`, reconstructed by walking `messages` and matching each `tool` result back to the `search_portal_layers` call that produced it via `tool_call_id`), then - if nothing close - against the results of a fresh `search_portal_layers` call using the title as the query. Either way, the id/url actually handed to the browser as a `pendingAction` always came from a real portal search; a title with no close match anywhere returns an error (with up to 3 suggested titles from the fresh search) instead of ever proposing a fictional layer.
- **Custom display name is resolved deterministically server-side, not asked of the model (2026-08, final form).** `item.title` in `add_portal_layer` is only ever used to *find* the layer (see above) - the layer is added under the real portal item's own title, so "add X and call it Y" needs a rename afterward. Two successive model-dependent designs for that rename both failed in production against `qwen2.5:1.5b`:
  1. A sibling `name` argument on `add_portal_layer` itself. The model reliably omitted the field, *even after it was marked `required` in the JSON schema* - required-in-schema is not enforced-in-output for every model/runtime.
  2. A separate `rename_layer(id, name)` client tool the system prompt asks for as a follow-up call, on the theory that a small model handles two simple sequential calls better than one compound one (it does handle the `apply_buffer` → `create_buffer_result_layer` chain correctly). Observed directly: "add Singapore Boundary and name it SCB" added the layer under its real portal title, never called `rename_layer` at all, and then **told the user it had renamed it** - a false claim the user could see contradicted by the layer's own row in the Layers card.
  The lesson this app now bakes in is not "prompt harder": **a step that must happen is not something to ask a small local model for.** The naming clause is already unambiguous in the user's own message, so `chatLoop.js`'s `renameOwedAfterAdd` derives the rename from that text and returns it as a `pendingAction` directly, with no model turn in between - structurally the same move as `resolveAddPortalLayerItem`, which likewise resolves a fact server-side rather than trusting what the model supplied. On the `/api/chat/tool-result` call reporting a successful `add_portal_layer`, it walks the round-tripped `messages` (so the service stays stateless) to find that call and the user turn that prompted it, extracts a requested name via `extractRequestedLayerName`, and - if it differs from the title actually added - pushes a synthetic `assistant` message carrying a real `rename_layer` tool call and hands that action to the browser. The browser executes it through `runClientAction`'s existing `rename_layer` branch (`GISMapEngine.renameLayer`, the same method the manual per-row rename control calls) and reports its result back under the synthetic `tool_call_id`, so the transcript the model eventually reads has the same shape it would have had if the model had asked. The auto-emitted call's own result cannot re-trigger the logic (its tool call's name is `rename_layer`, not `add_portal_layer`), so it fires at most once per add.
  - `extractRequestedLayerName` matches only explicit *"\<verb\> it/this/the layer \<name\>"* forms (`name it X`, `rename it to X`, `call the layer X`, `label it as X`), cutting the captured name at the next clause boundary so `"call it SCB and then zoom to it"` yields `SCB`. A bare `named X` is deliberately **not** matched: it far more often identifies which layer to add ("add the layer named Parks") than renames the one just added, and a false positive here silently mislabels a layer. Patterns match literal single spaces against whitespace-collapsed input rather than using `\s+` next to optional groups, since this text arrives from a request body and the ambiguous form backtracks super-linearly.
  - `rename_layer` **stays** in `CLIENT_TOOLS` and stays in the system prompt: the model can still call it for phrasings the deterministic path doesn't match, and for a standalone "rename layer X to Y" request with no add involved. The system prompt gained one line telling the model never to claim a rename that has no successful `rename_layer` result in the transcript, and not to repeat one that already applied the requested name - both the false-claim behavior above and a redundant duplicate rename after the automatic one.
  - Covered by `mcp-chat-proxy/chatLoop.test.js` (the service's first tests, `node --test` via its own `npm test`) and `ApplicationShell.test.jsx`'s `runClientAction add_portal_layer`/`runClientAction rename_layer` tests. `chatLoop.js` also logs every tool call (name + args, including auto-emitted ones) to `docker logs` - there was previously no visibility into what a model actually sent, which made this whole class of failure hard to diagnose without guessing.

  - **Sequential is still better than compound where the model *is* the right executor.** Design (2) above was not wrong as a general principle - `apply_buffer` → `create_buffer_result_layer` is the same shape and the model handles it correctly - and it stays this app's default for genuinely model-driven multi-step work. It's specifically unsuitable when the follow-up step is *mandatory to satisfy the user's request*, because a skipped optional-looking call is indistinguishable from a completed one to everything downstream except the user's own eyes.
- **Prompt injection.** `chatLoop.buildSystemMessage` explicitly labels the map-state JSON and instructs the model to treat every tool result as data, never as an instruction - a layer name, a portal item's title/snippet, or feature attribute text a tool result surfaces should never be able to redirect the model's behavior.
- **Authorization.** Every client-executed action reuses the real engine method, so it's bound by the same anonymous-first checks (`IdentityManager.findCredential`, `canEdit`) the manual UI already enforces - chat cannot do anything a signed-in-or-not user couldn't already do by clicking through the UI themselves.

## Configuration - nothing is hardcoded

See `mcp-chat-proxy/README.md`'s full table. In short: `OLLAMA_URL`/`OLLAMA_MODEL`/`ARCGIS_PORTAL_URL` are required and the service fails loud at startup if any are missing (same convention as `onemap-proxy`'s `ONEMAP_EMAIL`/`PASSWORD` check); no model name is assumed anywhere in code. `CHAT_ENABLED_TOOLS` lets an operator allow-list a subset of tool names (e.g. read-only). `VITE_CHAT_ENABLED` (read via `ArcGISConfiguration.js`'s `CHAT_ENABLED`, same `getEnv`/`window.__ENV__` runtime-override mechanism as `VITE_ARCGIS_PORTAL_URL`) gates whether `ChatPanel` renders at all. `OLLAMA_KEEP_ALIVE`/`OLLAMA_UNLOAD_AFTER_TURN`/`OLLAMA_NUM_PARALLEL` govern how much RAM Ollama holds between messages - see Memory above.

## Memory: the model's residency is the real cost, not this service

`mcp-chat-proxy` is stateless and holds nothing between requests (see Deliberately excluded) - what actually consumes RAM on a small instance is Ollama keeping the model *resident* so the next request skips the load. Weights plus a KV cache sized by `OLLAMA_NUM_CTX` sit there for the whole idle timeout (Ollama's default: 5 minutes) after the user's last message. `OLLAMA_NUM_CTX=2048` in this repo's `.env` was an attempt to squeeze that onto a 2GB instance, and it is the wrong lever - a context window too small to hold the 13 tool schemas (~2,260 tokens serialized) gets silently truncated by Ollama, and the model, no longer able to see the tool definitions, answers in prose describing the call it wanted to make instead of emitting a real `tool_calls` entry. Three better levers now exist, all env-driven and all defaulting to prior behaviour except where noted:

- **`OLLAMA_NUM_PARALLEL=1` / `OLLAMA_MAX_LOADED_MODELS=1`** on the Ollama container itself, now the default in `docker-compose.yml` and `deployArcGISReact.sh`. Ollama allocates the KV cache for *all* concurrent slots at load time, so cache RAM is `num_ctx` × slots; this app has one chat panel and one model. The largest saving of the three, and the only one that costs nothing at all.
- **`OLLAMA_UNLOAD_AFTER_TURN`** (default `false`). `chatLoop.js`'s `releaseModelAfterTurn` calls `ollamaClient.unloadModel()` - Ollama's documented empty-`messages`-plus-`keep_alive: 0` request - when a turn genuinely ends. The distinction it exists to make, and the reason this is not simply `OLLAMA_KEEP_ALIVE=0`, is that **a `pendingAction` return is not the end of a turn**: the browser runs that map action in milliseconds and returns immediately to `/api/chat/tool-result`, so evicting there would reload the model in the middle of one user request. Only a final text reply - or a thrown turn, which is the last case that should leave RAM pinned - releases it. `runLoop` is a thin wrapper around `runLoopUntilDone` purely so that decision lives in one place and covers the throw. The unload is fire-and-forget: the user's reply never waits on it, and a failed unload is logged as a missed optimisation rather than surfaced as a failed chat.
- **`OLLAMA_KEEP_ALIVE`** (default: unset, inheriting Ollama's own). Passed through per request by `ollamaClient.js`'s `withKeepAlive`, overriding whatever the Ollama server was started with. A plain idle timer with no notion of turn boundaries - useful as a short-duration safety net (`"30s"`) alongside the option above, for the case where a browser abandons a turn and never comes back to finish it, but a poor primary choice for the reason given there.

What all this buys back is model load time on the next message - seconds from page cache - against the ~200s of prompt evaluation a CPU-only turn already spends. Covered by `chatLoop.test.js`'s final-answer / mid-turn / failed-turn / option-off / failed-unload tests.

## Infrastructure

- `nginx.conf`'s `/api/chat/` location proxies to `mcp-chat-proxy:4001`, same same-origin/re-resolve-per-request pattern as the existing `/api/onemap/` block (with a longer `proxy_read_timeout`, since a local-model turn can run well past nginx's 60s default).
- `docker-compose.yml` adds `mcp-chat-proxy` and an **optional** `ollama` service (official image, named volume for model weights, not published to the host) - `ollama` is a convenience default, not load-bearing infrastructure the way `onemap-proxy` is for geocoding; an operator already running Ollama elsewhere just points `OLLAMA_URL` at it.
- `deployArcGISReact.sh`'s manual multi-container path starts `ollama` then `mcp-chat-proxy` on the same shared `arcgis-network`, mirroring `onemap-proxy`'s existing build-and-push-the-image-yourself precedent.
- `docker-entrypoint.sh` forwards `VITE_CHAT_ENABLED` into `env-config.js` alongside the existing `VITE_ARCGIS_*` values, so it's a true runtime (not build-time) toggle.

## The transcript is bounded (2026-08)

`ChatPanel`'s `protocolMessages` is round-tripped in full on every request, and until now it only ever grew. `services/chatTranscript.js`'s `trimTranscript` caps the retained array at 128 KB, dropping whole oldest exchanges. It cuts **only on user-turn boundaries** and runs **only at the start of a new user turn** - both because an assistant `tool_calls` entry and its answering `tool` message are paired by `tool_call_id`, and `knownPortalItems`/`renameOwedAfterAdd` above walk this array relying on exactly that pairing. See `knowledge/features/performance.md` §4 for the full rationale and the memory cost it removes.

Note the interaction with this service's statelessness: because `chatLoop` echoes back the messages it was sent, a trim on the client propagates into what the model sees on later turns. Dropping the oldest exchanges therefore drops that context for the model too - an accepted trade, since `OLLAMA_NUM_CTX` truncates the prompt long before a 128 KB transcript could reach the model anyway.

## Deliberately excluded

- No conversation persistence - `mcp-chat-proxy` holds nothing in memory or on disk beyond the in-flight request; a page refresh clears the chat history (`ChatPanel`'s local component state).
- No streaming responses (the sidecar's Ollama calls are `stream: false`) - a first-pass simplicity choice, revisit if turnaround time on larger local models makes it worth the added complexity.
- No multi-tool-call-per-turn client-action batching - if a single assistant turn calls more than one client tool, only the first is executed; the model is expected to ask again for the rest once it sees that one's outcome.
